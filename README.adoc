== Descripción general

Este proyecto es un MVP para un sistema de reserva de aparcamiento diseñado con el objetivo de soportar alta concurrencia y picos masivos de tráfico dentro de un flujo de reserva sencillo.

El sistema está diseñado para como un conjunto de microservicios independientes basados patrones de diseño modernos, con una arquitectura hexagonal (Ports & Adapters) separando las responsabilidades de cada dominio. La coordinación entre servicios se realiza mediante eventos asíncronos en Kafka, y la autenticación con el frontal gestiona con Keycloak utilizando OAuth2/OIDC.

== Diseño

=== Descomposición en módulos

Al diseñar el sistema el enfoque ha sido en primer lugar la identificación de los *bounded contexts* del dominio y la definición de los microservicios correspondientes, asegurando una clara separación de responsabilidades y un acoplamiento bajo entre ellos. Dentro de esta separación de lógica los problemas identificados son:

- *Gestión de catálogo de aparcamientos y disponibilidad*: sistema que permite búsquedas sobre parkings disponibles en función de criterios de búsqueda (ubicación, fechas, etc) y lleva el control de las plazas disponibles estableciendo mecanismos de bloqueo para evitar sobreventa bajo alta concurrencia.

- *Gestión del ciclo de vida de una orden de compra* a partir de un hold de plaza de aparcamiento gestiona el ciclo de vida de una orden de compra e interactúa con los sistemas de pago.

- *Sistema de cálculo de tarifas* configurable y dinámico en función de la disponibilidad. Ofrecerá tarifas bajo demanda, permitirá establecer reglas para mantener una proyección de precios para las búsquedas.

- *Modelo de autenticación híbrido* para permitir operaciones anónimas (búsquedas e intento de bloqueo de un slot) y operaciones autenticadas (procesado del _Order_).

- *Sistema de búsqueda geográfica* que permita búsquedas indexadas por criterios de nombre, keywords establecidas en un Parking (como por ejemplo estaciones, aeropuertos cercanos, museos o cualquier otro punto de interés) y que se integre con el buscador del catálogo para permitir autocompletado en las consultas.

A partir de estas premisas y dado que no existen requisitos funcionales específicos se el diseño se ha realizado tomando las siguientes decisiones:

- Dentro del compromiso entre escalabilidad y consistencia en el sistema de bloqueos se ha optado por la escalabilidad. Cuando un usuario realiza una búsqueda de parking, en lugar de realizar un bloqueo agresivo de todas las plazas disponibles para mantener un precio fijo desde la búsqueda hasta la reserva, se ha optado por un sistema de cálculo aproximado de precios usando una proyección generada por el módulo de precios. +
Cuando un usuario realiza una búsqueda el sistema no realiza los cálculos complejos de tarificación (enviando todas las ventanas de tiempo y su disponibilidad) y sólamente devuelve una estimación de precio que posteriormente será calculada en el momento de comenzar el proceso de reserva.
Este sistema tiene el handicap de no ofrecer inicialmente un precio fijo al usuario pero a cambio hace que el modelo de búsqueda sea mucho más ligero y no implique el bloqueo de plazas en la búsqueda. Este funcionamiento no ofrece un precio fijo y puede generar una mala experiencia, pero para picos de demanda masiva es mas esalable y se pueden diseñar políticas de estimación con alta precisión. +
El módulo de pricing irá procesando los eventos de cambios de disponibilidad y a partir de sus reglas de cálculo irá actualizando esta proyección de precios para que el sistema de búsqueda pueda ofrecer una estimación lo más precisa posible.

- Autenticación híbrida. Los requisitos no establecen si un usuario sin autenticación puede realizar una reserva. En la implementación se ha optado por un modelo en el que para el comienzo del proceso de reserva no es necesaria la autenticación pero para la confirmación si que es necesario el registro.

- Reservas de baja duración vs reservas de larga duración. El sistema contemplará estos casos de uso que tendrán procesos de bloqueo de slots diferentes:

** Bloqueos de corta duración para estacionamiento en tramos de media hora. Este sistema estará más orientado a obtener tarifas dinámicas en función de la demanda y ofrecer una experiencia de reserva rápida para usuarios que quieren aparcar durante un periodo limitado.

** Bloqueos de larga duración para reservas de días o semanas enteras. En este caso las operaciones de bloqueo de ventanas de media hora puede afectar a gran cantidad de registros de modo que ha optado por un modelo de bloqueo de ventanas de 24 horas para este tipo de reservas.

Con esta idea se ha modelado el sistema en el que un parking de N plazas tiene una asignación diferente para cada ventana de disponibilidad. Esta ventana no tiene por que ser fija y el sistema podría ajustarla dinámicamente en función de la demanda. 

De este modo por ejemplo un aparcamiento de 1000 plazas podría tener:

- 600 plazas asignadas a bloqueos de *corta* duración.
- 300 plazas asignadas a bloqueos de *larga* duración.
- 100 plazas flexibles que se asignan dinámicamente en función de la demanda de cada modelo de venta.

También, este modelo no tiene por que ser estático y el sistema pudiera actualizarlo en función de las reglas de negocio que se decidan para maximizar la ocupación del parking y se adapte mejor a los picos de demanda.

=== Módulos y responsabilidades

image:../diagrams/c4-container-diagram.png[width=100%]

==== Módulo prs-ms-parking-facilities

Este componente es el responsable de la gestión del catálogo de aparcamientos. Tiene las responsabilidades principales de:

*Responsabilidades:*

- Mantener el catálogo de aparcamientos, plazas y su disponibilidad.
- Buscar plazas en función de criterios de búsqueda (ubicación, fechas, etc).
- Gestionar el sistema de bloqueo de plazas (hold) para evitar sobreventa bajo alta concurrencia.
- Servir como fuente de aparcamientos para el módulo de búsquedas geolocalizadas.

TIP: esté módulo podría descomponerse en dos microservicios independientes, uno que sólo llevase el catálogo de aparcamientos y otro que gestione el sistema de bloqueo de plazas. No obstante y para que el MVP no sea excesivamente complejo, se ha optado por mantener ambas responsabilidades en un mismo módulo.

==== Módulo prs-ms-ecommerce

Este módulo es el responsable de gestionar el ciclo de vida de una orden de compra.
No conoce los detalles del aparcamiento, bloqueos ni tarifas ya que cuando llega la orden de compra esta ya tiene un precio fijado y el proceso de reserva se ha iniciado.

Cuando se inicia un proceso de reserva el módulo simplemente orquestará el pago del cliente y se emitirán los eventos correspondientes.

Dentro de las consideraciones de este sistema y teniendo en cuenta que desde el sistema de bloqueo que ofrece una tarifa bloqueada durante un tiempo, de cara a la consistencia el sistema primará los tiempos de expiración de los bloqueos antes que una política de "periodo de gracia entre que el usuario paga y el bloqueo expira". Esto es peor para la experiencia de usuario pero para un MVP resulta mucho mas sencillo de implementar que un sistema de reintento que obligaría a tener una política de re-hold.

*Responsabilidades:*

- Establecer el flujo de una orden de compra: hold, pago, confirmación, cancelación.
- Conoce los mecanismos de pago.
- Sabe gestionar procesos de devolución de pagos y cancelaciones para cada sistema de pago.

==== Modulo prs-ms-pricing

Este módulo es el responsable de establecer las reglas de negocio para el cálculo de tarifas de cada reserva.

Dentro de un modelo de tarificación podríamos tener tarifas fijas por hora/día, tarifas ajustadas a la demanda, descuentos por duración de la reserva, promociones, etc.

Dentro del MPV y bajo la premisa de la escalabilidad este sistema no es consultado en cada búsqueda, únicamente cuando el usuario comienza una reserva. Para el MVP se simplificarán estos modelos y la asbtracción de este módulo será:

*Responsabilidades:*

- Establecer las reglas de negocio para establecer el precio de una reserva.
- Generar proyecciones de precios para cada parking en función de su disponibilidad.

==== Módulo prs-ms-geo

Este módulo es el mas tonto de todos. Sólo sabe facilitar las busquedas de autocompletado de ciudades, aeropuertos y parkings. No tiene lógica de negocio ni nada complejo, simplemente es un sistema de búsqueda geográfica que reacciona a los cambios de _parking-facilities_ y ofrece una sistema indexado de búsqueda para el frontend.

*Responsabilidades:*

- Ofrecer un sistema de búsqueda geográfica para el frontend.
- Mantener un índice de ciudades, aeropuertos y parkings para facilitar las búsquedas.

==== Módulo prs-ms-users

Este módulo es el responsable de la gestión de usuarios a través de Keycloak.

*Responsabilidades:*

- Administrar perfiles de usuario (datos del cliente, métodos de pago, matriculas asociadas, etc).
- Creación parcial de usuarios en Keycloak para el proceso de reserva (registro durante el proceso de compra)

==== Módulo prs-ms-bff

Fachada de módulos de contratación usados por el frontend. Si bien este componente añade una capa adicional de complejidad, permite desacoplar comportamientos específicos como el modelo híbrido de autenticación anónima/autenticada, reglas de seguridad específicas (por ejempo manejo de sesiones anónimas de compra, cookies, bloqueos por IP, etc). De este modo hacemos que el resto de módulos no tengan que tener en cuenta esta lógica y se centren únicamente en su responsabilidad principal. De este modo también reducimos las reglas de seguridad la superficie de ataque a un único módulo. Esta es la única API expuesta al exterior mientras que el resto de componentes permanecen aislados dentro del orquestador de microservicios.

NOTE: Por cuestiones de tiempo se han incluído operaciones de administración directamente en el frontal y este consume APIs internas. Esto no sería lo deseable en un sistema real.

*Responsabilidades:*

- Establecer políticas de seguridad específicas para el frontend (sesiones anónimas, bloqueos por IP, etc).
- Delegación de llamadas a los módulos backend correspondientes.

=== Arquitectura

Para la implementación basada en Java las reglas que se han seguido son:

- Uso de *Spring Boot 4.x* (early adopter) que tiene aún problemas de integación con algunas librerías que aún no han sido actualizadas como _resilence4j_.

- Uso de *Axon 4.13* para la gestión de eventos internos y coordinación de procesos asíncronos. Para el MVP se ha optado por no usar ni AxonServer ni Event Sourcing, únicamente por las capacidades de CQRS y gestión de Sagas sin requerir de una implementación manual. Para la integración hacia el exterior se usará Spring Cloud Stream con el binder de Kafka.

- Uso de *Spring Cloud Stream* para la integración de Kafka. Aunque Axon tiene capacidades de integración con Kafka, para mantener un diseño más desacoplado. De este modo también podemos usar este mecanismo para los microservicios que no usan Axon manteniendo la misma estrategia de integración.

- Se ha *descartado el uso de Weblux* para este MVP ya que si bien el modelo reactivo aporta mejoras en la gestión de la concurrencia, añade una complejidad adicional al prototipo que se centrará más en la lógica de negocio. Podrían usarse Virtual Threads de Java 21 en entornos de alta concurrencia para mejorar la concurrencia sin añadir la complejidad del modelo reactivo, pero para el MVP se ha optado por el modelo tradicional de hilos. Donde podría encajar más es el módulo BFF donde permitiría mejoras en el caso de manejar SSEs.

- Para la comunicación síncrona a través de APIs REST entre módulos se ha usado el plugin `org.openapi.generator` de _Gradle_ usando la modalidad `restclient` adaptada para las dependencias de Spring Boot 4 y Java 21 (uso de anotaciones de Jakarta y Jackson 3+).

- No se creará ninguna librería compartida entre módulos. Cada uno de ellos será completamente independiente. En un escenario real si que sería considerable crear librerías comunes a modo de _starters_ de Spring como por ejemplo para Guards de seguridad, modelo extensible de eventos, interfaces para trabajar con Command/Queries con autenticación, RSQL o cualquier otra funcionalidad común.

- Otras decisiones de diseño han sido:

** Uso de *PostgreSQL* como base de datos principal con un modelo relacional tradicional con separación por dominios.
** Uso de *SpringDoc* para la generación de documentación OpenAPI.
** Uso de *Redis* como caché distribuída.
** Uso de *Spring Cloud Config* para la gestión centralizada de la configuración y reutilización de configuraciones comunes.
** Uso de *Mapstruct* para el mapeo entre entidades y DTOs.
** Uso de *Lombok* para reducir el código boilerplate.

[TIP]
====
Se ha optado por una aproximación pragmática a la hora de realizar la separación de capas dentro del paradigma de arquitectura héxagonal usando Axon. Si bien una separación purista de capas haría que el uso de elementos como @Aggregate o @Saga estuvieran a nivel de infraescructura, para aprovechar las ventajas de estos frameworks y evitar niveles de abstracción innencesarios se ha optado por aceptar este acoplamiento a nivel de la capa de aplicación. Si bien es posible aislarlo, al hacerlo se pierden muchas de las ventajas de usar Spring y se requiere de mas código manual para gestionar aspectos que el framework ya gestiona de forma automática.
====

=== Axon, Sagas y esos extraños compañeros de cama

La idea de usar Axon es para mantener una coherencia dentro del modelo de eventos que sea fácilmente entendible y ahorrarme lineas de código. Podría haberse sustuituído por otro modelo de gestión de eventos como Spring Cloud Stream y una implementación manual de llamadas a servicios ya sea de un modo coreografiado o de un modo orquestado. Para el caso en el que lo he usado es para centralizar los casos de uso que implican el tratamiento de los eventos que han sucedido en el sistema independientemente de cual haya sido su origen (eventos locales manejados por el framework, commands publicados en el bus interno vía Spring Cloud Stream o a través de un controlador REST o cualquier otro servicio del sistema).

Este patrón desacopla la lógica de servicios ya que las interfaces externas simplemente reaccionarán emitiendo eventos independientemente de cómo han sido generados (no sólo eventos, normalmente interaccionarán con el Command/Query Gateway que es una abstracción sobre este sistema).

Dentro de estas consideraciones hay que tener en cuenta la naturaleza de cada evento y de si se requiere de una consistencia fuerte usando el patrón Outbox o si simplemente es un evento que se puede emitir localmente para luego ser tratado por otros componentes (principalmente por proyecciones que lo publican en sistemas externos).

Para el primer caso usaríamos una escritura transaccional dentro del mismo contexto que realiza la operación (mismo @Transactional) y un dispacher de eventos que gestione su publicación. Dentro de este MVP no se ha implementado ya que en los casos donde tiene sentido (aquellos de gestión de dinero) ocurren fuera del sistema y los casos de uso que no lo usan no se han definido como críticos: por ejemplo, si un proceso de bloqueo de una plaza falla el sistema llegado a su deadline lo compensará automáticamente. Se habrá bloqueado un slot X tiempo pero tampoco puedes hacer mucho mas en este caso porque tu infraestructura está muerta.

Siguiendo este modelo, el uso del framework no deja de ser una comodidad que tenemos respecto a crear todos los servicios tradicionales a través de los cuales gestionaríamos los mismos casos de uso.

Una de las ventajas de este sistema es que podemos controlar de que forma un servicio interactúa con la saga: si es un mecanismo que se puede ejecutar de forma aśincrona con posibilidad de fallo a modo de proyección como un manejador de eventos, o de si es un proceso crítico que requiere un tratamiento diferente y entonces no sería tratado como un evento emitido sino como parte de una unidad de procesamiento transaccional.

Un ejemplo de esto es el `ReservationCreatedStreamPublisher`. Este componente define que es un `@EventHandler` de un determinado tipo de evento que sucede en el sistema que sucede en otro ámbito de ejecución al del procesamiento del order. En este caso, si la publicación del evento falla, puede aceptarse que es un mal asumible porque se trataría de una degradación completa del sistema sin que esto afecte a lo importante que son las órdenes de pago: "sentimos no poder confirmar su reserva".

Para casos donde si que es necesario un tratamiento consistente no usaríamos manejadores de eventos sino que dentro de la lógica de la saga nos aseguraríamos de que el evento ha sido tratado adecuadamente antes de seguir el flujo asíncrono que publicación de eventos de Axon (y luego por Cloud Stream).

NOTE: Nunca he usado Axon en entornos productivos porque generaba un alto grado de acoplamiento respecto a un framework que no está tan extendido, pero si que en todos los lugares donde he estado desde hace un tiempo al menos hice una POC para comparar su funcionamiento respecto a otros sistemas como Eventuate o una implementación manual de los procesos de transaccionalidad distribuida y sistemas de compensación.

NOTE: Dentro del modelo de comunicación basado en Spring Cloud Stream la configuración es cero. Se define el comportamiento de cada consumidor y productor sin más. En entornos reales esta configuración estará ajustada a un duncionamiento más robusto como poíticas de reintos, gestión diferente de tipos de excepciones, etc.

==== Sagas dentro del ejercicio

Las principales son las del proceso de reserva y la del tratamiento de orders. En el primer caso el problema principal es que una Reserva confirmada (con bloqueo de plaza) se quede indefinidamente bloqueada en el sistema (las que no están cofirmadas se purgan automáticamente con el `@DeadlineHandler` que establece su TTL).

En el segundo caso, las órdenes de compra tienen una expiración que viene determinada por el valor del hold y que se recibe dentro del evento. Pasado ese tiempo se marca como expirada, y se emite el evento correspondiente para que el sistema de gestión de disponibilidad libere dicha plaza.

En ambos casos una degradación del sistema no impacta de forma crítica en el funcionamiento. Ante una catástrofe el sistema seguirá manteniendo bloqueos de plazas, que es un problema gordo porque dejas de facturar, pero si ha fallado el proceso es que tu sistema está caído y si todo está mal, pues tampoco puedes hacer mucho mas.

Una consideración interesante sobre este modelo sería que la pasarela de pago si que tuviese este comportamiento: "el usuario X ha pagado pero no se ha podido hacer una llamada OK al sistema de recepción de pagos". También, en este caso la responsabilidad de asegurar la consistencia sería del sistema externo, no el de _ecommerce_ que sólo es capaz de manejar la información que le ha llegado. Para este ejercicio no se contempla: es una llamada REST sícrona y si el sistema está caído y no recibe la request pues lo seguirá considerando como un impago.

De este modo, para el ámbito del ejercicio el modelo de Outbox no se ha tenido en cuenta dado que en los casos donde el sistema falla la compensación es automática dentro del deadline de cada operación (la de la reserva que es la que determina también la de la orden de compra).

=== Seguridad

El sistema tiene la particularidad de aceptar operaciones anónimas para la búsqueda y bloqueo de plazas pero requiere autenticación para la confirmación de la reserva. Para esto se ha diseñado un modelo híbrido en el que el módulo BFF es el encargado de gestionar esta lógica y delegar las operaciones a los módulos backend correspondientes.

Para la autenticación a través del frontend se utilizará *OIDC* con Keycloak como proveedor de identidad. En las operaciones *anónimas* el sistema generará un identificador de sesión anónimo que se usará para mantener el contexto de la reserva durante el proceso de compra. Este *identificador se mantendrá en una cookie* y se usará para asociar las operaciones de bloqueo y reserva con la sesión anónima correspondiente. En caso de que el usuario decida autenticarse durante el proceso de compra, el sistema podrá asociar la sesión anónima con el perfil de usuario autenticado para futuras referencias.

==== Clientes de Keycloak

Este prototipo incluye dos clientes de Keycloak para gestionar la autenticación creados por _Terraform_:

- _parking-client_ con autenticación para las comunicaciones Backend to Backend utilizando client credentials.
- _parking-client-frontend_ con autenticación PKCE para las comunicaciones del frontend SPA con los backends.

==== Consideraciones de la implementación

Aunque Spring Security permite activar `@EnableMethodSecurity` para establecer las restricciones de los métodos a través de anotaciones como `@PreAuthorize("hasAuthority('parking:create')")`, este mecanismo no encaja demasiado bien con un modelo de Arquitectura Hexagonal ya que un funcionamiento crítico como la seguridad quede acoplado al framework. Para evitar esto se optará por crear Guards programáticos con el modelo _port/adapter_ de un modo similar al siguiente:

[source, java]
----
public interface ParkingAccessGuardPort {
    void canCreateParking(CurrentUser user);
    void canUpdateParking(CurrentUser user, UUID parkingId);
    // ...
}
----

Esto nos permitirá una mejor granularidad a la hora de establecer las reglas de seguridad y podrá ser testeada como un componente más de infraestructura.

=== Observabilidad y monitorización

El MVP usa OpenTelemetry y Prometheus para la monitorización de los servicios a través de Actuator. Para esto se ha incluido un colector de OpenTelemetry que exporta las métricas a Prometheus y esta a su vez las expone para ser visualizadas en Grafana.

Verificaremos primero que las métricas de Actuator están funcionando, por ejemplo con el servicio de parking-facilities:

http://localhost:8081/actuator/prometheus

Y después comprobar que desde Prometheus se están recogiendo las métricas:

http://localhost:9090/query?g0.expr=jvm_memory_used_bytes

== Ejecución local

Para ejecutar el proyecto localmente primero compilaremos los proyectos Java con _gradle_ para ver que todo compila correctamente. Para esto ejecutaremos el siguiente comando desde la raíz del proyecto:

[source, bash]
----
./gradlew clean build -x test
----

Si todo ha ido bien, el siguiente paso será levantar los servicios de infraestructura necesarios para el funcionamiento del sistema. Para esto se ha incluido un fichero _docker-compose.yaml_ con la definición de los servicios necesarios para el desarrollo local. Se han definido los siguientes perfiles:

- `infrastructure`: para los servicios de infraestructura (PostgreSQL, Redis, Kafka, Keycloak, Prometheus, Grafana, OpenTelemetry y el servidor de configuración basado en Spring Config Server).
- `apps`: para los microservicios y frontends.

En primer lugar levantaremos los servicios de infraestructura y usaremos _Terraform_ para crear la configuración del _Realm_ de Keycloak.

[source, bash]
----
cp .env.example .env
# editar .env con tus credenciales y configuraciones
docker compose --profile infrastructure up -d --build
----

[TIP]
====
Para partir de un entorno limpio borraremos los volúmenes ejecutando:

`docker compose --profile infrastructure --profile apps down -v`
====


Después desde las carpetas de terraform ejecutaremos los comandos de inicialización y aplicación de la infraestructura:

[source, bash]
----
cd terraform
cp terraform.tfvars.example terraform.tfvars
# editar terraform.tfvars con tus credenciales
terraform init
terraform plan
terraform apply
----

Una vez creada la infraestructura ejecutaremos la build para compilar los microservicios y frontales:

[source, bash]
----
docker compose --profile apps up -d --build
----

Una vez tengamos levantadas las APIs necesitaremos cargar algunos datos de ejemplo como las reglas de tarificación o unos parkings de prueba. Para ello dentro de la carpeta _resources/data-initialization_ tenemos un script que hace la carga inicial usando CURL y ficheros JSON:

[source, bash]
----
cd resources/data-initialization
./initialize-entities.sh
----

Si todo ha ido bien podremos hacer una petición para listar los parkings disponibles:

[source, bash]
----
curl --location 'http://localhost:8081/api/v1/parking-facilities?page=0&size=1' | jq
----

=== Pruebas de estrés

Dentro de la carpeta _resources/stress-basic-tests_ tenemos algunos scripts para hacer unas pruebas muy básicas de estrés sobre el sistema.

Para ejecutar los scripts usaremos el comando time para medir los tiempos totales y pasaremos como argumento el número de peticiones y el nivel de concurrencia. Por ejemplo, para ejecutar 1000 peticiones de bloqueo con una concurrencia de 100:

[source, bash]
----
$ time ./basic-reservation-stress-test.sh 1000 100
Fetching facility ID from catalog...
Using facility ID: 2e707e7a-5e04-4491-ac32-26c7ef48b697
Sending 1000 requests with concurrency 100...
  HTTP 201 : 1000 requests
Total time: 1s

real	0m0,686s
user	0m4,689s
sys	0m3,761s
----
